## 1. 项目定位与原则

- 在官方 web.telegram.org（Web A 与 Web K 两版）页面内运行的用户脚本（Tampermonkey/Violentmonkey），
  把聊天归档进用户自己的私有频道，**不需要 api_id/api_hash**。
- 页面必须保持打开；脚本只读取“当前登录用户已经能看到的内容”（DOM），不改动 Telegram 服务器端数据。
- 写入路线按保真度分为三条：
  - `snapshot`（气泡截图，当前主力）：把每条消息渲染成 PNG 发进频道；
  - `copy`（文字重发 / allow_media 时媒体下载重发）；
  - `forward`（调用页面原生转发，保真度最高）——v0.5.0 起提供实验性实现，选择器需真机校准。
- 受保护聊天默认 `skip`；高级策略 `text_only` / `allow_media` 需要用户逐聊天显式开启。
- Telegram Web 改版频繁，DOM 选择器一律以「① 探测 DOM」输出为准做校准，不承诺长期稳定。

## 2. 已实现（v0.3.1 现状；v0.5.0 增量见第 0 节）

### 2.1 面板与操作
- 页面右下角悬浮面板：归档频道、模式（snapshot/copy）、保护策略、开始/停止、重试/清理队列、
  探测 DOM、重置进度、收起。
- 模式/频道/策略会记忆到脚本存储，刷新后保留。

### 2.2 snapshot（截图）核心链路
- 流式“截图 1 张 → 切到归档频道 → 发送 1 张 → 切回源聊天”，任意时刻内存只持有 1 张截图。
- 两个方向：
  - 「⚡ 截图到最新」：从当前阅读位置向下增量；
  - 「▲ 向上回溯」：从底部向上补旧，遇到断点/顶部停止。
- 每条成功消息记录断点 `check:<peer> = {mid, ts}`，失败项进重试队列（附截图元数据）。
- 日期解析按 `data-timestamp` → `time.datetime` → 标题/时间文本逐级回退，取不到标“未知日期”，
  绝不退回“当前时间”。
- caption 自动生成：
  `📎 图片/视频/… · 📅 原时间（· 发送者）` + `#media_* #date_YYYY_MM_DD`，
  便于在频道里按类型/日期检索。
- v0.3.1 修复：发送前必须确认截图**真的进入输入框**（drop → paste → 文件框逐种尝试，
  以“输入框出现媒体预览 + 上传结束”为准）；附加失败则整条进队列、**绝不只发 caption 文字**。

### 2.3 copy 与媒体路线
- copy：文字消息带发送者前缀重发（群聊场景）。
- copy + allow_media：对可见消息里的 `stream/…` 媒体地址分片 fetch → Blob → File →
  注入输入框发送（沿用 Telegram-Media-Downloader 思路）。**当前未经真机校准，报错属预期。**

### 2.4 校准工具
- 面板「① 探测 DOM」：输出 A/K 下的聊天标题、气泡、发送按钮、输入框等 DOM 快照并复制到剪贴板。
- `probe.mjs`：开发侧 Playwright 探测器，弹出 Chromium 让真人扫码登录后抓取 DOM 结构到 `/tmp/tgwa-probe`。

## 3. 待实现功能（按优先级）

### P0 —— 正确性与可靠性（先做）

1. **附件注入真机校准（Web A / Web K）**
   - 背景：0.3.1 之前合成 drop 不被页面接受时，会只发出 caption 文字、没有图片（已在 0.3.1 加护栏，
     但“图片真能进输入框”仍未在 A/K 真机各验证一次）。
   - 要做：分别在 Web A 和 Web K 上跑通「附加截图 → 看到预览 → 发送 → 频道里是真图片」；
     确认 preview/上传进度的 DOM 信号与选择器；必要时补“真用户手势”注入方案。
   - 验收：snapshot 模式在 A、K 各连续归档 10 条媒体消息，频道内 0 条“只有 caption 没图”的假归档。

2. **发送成功判定**
   - 现状：发送后只看输入框是否被清空，仍可能误判（如上传失败、消息实际未发出）。
   - 要做：发送后校验“频道里真的多了一条消息”（时间/计数变化，或记录返回的 message id）。
   - 验收：人为制造发送失败（断网/删除频道）时，条目进队列而不是被标记成功。

3. **断点/去重改为按聊天隔离**
   - 现状：`done` 列表按应用级路径名 + 裸 mid 记录，不同聊天同 mid 会互相误跳过。
   - 要做：`done:<peer>` 按聊天分别存储；旧存储做一次性迁移。
   - 验收：两个不同聊天存在相同 mid 时，各自都能独立归档、互不跳过。

4. **重试队列持久化**
   - 现状：队列只存在内存，刷新页面即丢失（失败截图也会丢）。
   - 要做：队列元数据（含小尺寸失败截图或 PNG 的 IndexedDB blob）落盘，重开后可从队列续传。
   - 验收：归档中途刷新页面，失败条目仍可在新会话里重试。

### P1 —— 功能完整与保真度

5. **forward（原生转发）模式**
   - 要做：面板增加模式选项；调用页面原生“转发”对话框：搜索归档频道 → 选择 → 发送；
     识别受保护聊天的服务器拒绝并跳过；可保留原转发头。
   - 验收：普通聊天转发后保真度与手动转发一致；受保护聊天不产生半成品消息。

6. **相册/组消息处理**
   - 要做：识别同一相册的多张图片：可“整组 1 张截图”或“逐张截图”两种策略，
     组内消息不重复归档。
   - 验收：一个 5 图相册不会发成 5 张互相孤立的重复截图，也不会漏图。

7. **动态媒体（视频/语音/文件）**
   - snapshot：视频截当前播放帧并带 `#media_视频`；语音/文件气泡正常截出可辨识内容。
   - copy + allow_media：逐媒体分片取回、按原始文件名/类型重发；上传进度可见。
   - 验收：视频消息在频道里打开能看到画面或能播放，caption 类型标签正确。

8. **标签与检索规范化**
   - 要做：与 Telethon 版（`#chat_xxx / #user_xxx / #date_YYYY_MM`）对齐；
     频道内“按类型/日期/来源”检索保持一致；避免 caption 里的换行被 Telegram 截断。
   - 验收：在归档频道搜索 `#media_图片` 与 `#date_2026_09_04` 都能命中且只命中真实媒体消息。

9. **用户可配置项**
   - 截图倍率/格式（JPEG 可减小体积）、滚动步长与间隔、单次上限、
     发送前是否自动切换频道、上传等待时长。
   - 验收：面板能改并生效，设置持久化。

10. **进度与暂停恢复**
    - 要做：运行中显示当前位置、成功/失败/剩余数；支持“跑完当前条后暂停”，
      下次从断点继续；把「重置进度」的误操作影响写清楚（会清空当前聊天 done/check）。
    - 验收：100 条聊天分 3 次运行归档完成，无重复、无遗漏。

11. **频道侧幂等校验**
    - 要做：发送前先在归档频道搜索本条 caption（或本地记录已发送 message id），
      防止“消息已发出但脚本没记成功”导致重复归档。
    - 验收：重跑同一条只产生一份归档。

### P2 —— 体验与运维

12. **多聊天任务队列**：一个页面串行处理多个源聊天（各自的断点/方向/策略）。
13. **校准向导自动化**：probe.mjs 升级为半自动向导，抓取一次 DOM 后直接生成可写入脚本的选择器建议。
14. **频率控制与风控提示**：可调间隔 + 默认温和节奏；界面提示“自动化存在账号风控风险，建议小号”。
15. **错误分类与批量重试**：按“附加失败/发送失败/频道切换失败/内容受限/上传超时”分类展示与批量重试。
16. **归档统计/报告**：每次运行结束给出按类型/日期的汇总，方便核对。

## 4. 明确不做

- 不解析、不依赖 Telegram 内部 JS 私有对象（stream URL 读取除外）；
- 不做百万级无人值守全量归档；
- 不做多聊天并发调度（同页面只串行）；
- 不提供绕过登录/2FA/安全校验的能力；
- 不承诺绕过受保护聊天限制——`allow_media` 属高风险开关，仅作为用户自担风险的实验选项。

## 5. 建议开发顺序

1. P0-1/P0-2：真机跑通“附加 + 发送确认”（需要用户配合在 A/K 上各跑一次小批量并反馈日志/探测输出）；
2. P0-3/P0-4：按聊天隔离去重 + 队列落盘；
3. P1-5 forward、P1-6/P1-7 相册与动态媒体；
4. P1-8 ~ P1-11 检索标签、配置、进度、幂等；
5. P2 各项按使用反馈排期。

每个 P0/P1 条目完成时，README.md 同步更新“当前支持”与“已知限制”两节，并在频道里人工抽查
（真图片 + caption、无 caption-only 假归档、断点重启无重复）。
