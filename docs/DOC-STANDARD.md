# 文档规范

> 本文件是 `docs/` 的写作与维护标准。**所有新写、改写的文档都要满足这里的硬性要求**；
> 不符合的文档在 review 时不予合并。规范本身随实践演进，改动需在提交信息里写明理由。
>
> 适用对象：本仓库的维护者、外协开发者、以及接手的 AI 助手。

## 一、三条底线

1. **数字必须实测，写明来源。** 测试用例数来自 `pnpm test` 输出，部署版本来自
   `wrangler deploy` 输出的 Version UUID，迁移号来自 `db/migrations/`。禁止写
   "大约""可能有几十个""大概 200 条"——拿不到数就写"未测"，不要编。
2. **讲「为什么」，不只讲「是什么」。** 每一条结论都要能让读者回答两个问题：
   当时为什么要这样做？不这样做会出什么事？纯清单式 changelog 不合格。
3. **坏消息必须写。** 未做项、已知限制、失败过的尝试、需要人工补的步骤，一律
   单列章节写清楚。只写好话的文档视为不完整。

## 二、放哪、叫什么

目录归属与「什么时候看哪份」见 [`README.md`](README.md)，这里只列命名硬规则。

| 类型        | 目录        | 命名                                                                          | 例子                                          |
| ----------- | ----------- | ----------------------------------------------------------------------------- | --------------------------------------------- |
| 更新记录    | `releases/` | `RELEASE_YYYY-MM-DD.md`；同日多批加主题后缀                                   | `RELEASE_2026-10-29_PUBLICATION_HARDENING.md` |
| 报告        | `reports/`  | `WORK_REPORT_YYYY-MM-DD.md`（一轮工作）/ `PROJECT_REPORT.md`（长期总报告）    | —                                             |
| 审计        | `audits/`   | `*_AUDIT_YYYY-MM-DD.md` 或 `*AUDIT_YYYY-MM-DD.md`；截图放同名 `-assets/` 目录 | `CODE_AUDIT_2026-09-27.md`                    |
| 手册        | `guides/`   | 大写下划线，`主题.md` / `主题_GUIDE.md`                                       | `QUESTION_TYPES.md`                           |
| 运维        | `ops/`      | 小写连字符（`ops-*.md`）或大写下划线                                          | `ops-runbook.md`                              |
| 交接/路线图 | 根 `docs/`  | `HANDOVER*.md` / `UPGRADE_ROADMAP_YYYY-MM-DD.md`                              | —                                             |
| 历史留档    | `archive/`  | 保持原名，**不再新增**                                                        | —                                             |

规则：

- **日期一律 `YYYY-MM-DD`**，不写 `10/29`、`Oct29`。
- 文件名只允许字母、数字、`_`、`-`、`.`；不要中文文件名（链接在不同平台上易失效）。
- 同一主题的系列文档保持在同一个目录，用后缀区分（`_PART2`、`_SUPPLEMENT` 不许用，
  改写进同一份或加日期）。

## 三、通用骨架

除索引与留档外，每份文档**开头 10 行内**必须交代清楚四件事：

```markdown
# 标题（一句话说清这是什么）

| 项       | 值                                          |
| -------- | ------------------------------------------- |
| 状态     | 生效中 / 已完成 / 已取代 / 提案（未实施）   |
| 日期     | 2026-10-29（最后实质性更新）                |
| 适用版本 | Worker `86fa5644` / git `f9f8e5d`（可省略） |
| 相关     | 关联文档、迁移号、issue                     |
```

正文结构：

- 只有**一个 H1**；章节用 `## 一、二、三`（中文数字，本项目惯例）或英文短语，同一
  文档内不混用。
- 每节先说结论，再说细节。读者扫标题就该知道发生了什么。
- 表格只放**可枚举的事实**（字段、数值、状态）；解释写进表格前后的正文，不要把
  长句塞进单元格。
- 代码块必须标语言（`ts / `sql / ```bash）。命令要能直接复制执行。
- 不写密钥、Token、密码、内部账号密码。写"见 Secret `FOO`"即可。

## 四、各类文档的必备内容

### 4.1 更新记录（`releases/`）

读者是**用户与运维**，不是开发者。必备：

1. **引语**（blockquote）：2–5 行，说清这次发布用户能感知到什么、修掉了什么隐患。
2. **元信息表**（字段名固定）：`功能上线`（Version UUID + 时间 CST）、`线上入口`、
   `数据库迁移`（迁移号 + 是否已应用 + 老库降级行为）、`自动化测试`（`N 文件 / M 用例`
   - 与上轮对比）、`静态检查`。
3. **分章正文**：每章一个主题。新功能要写**默认值的选择理由**（例如"默认不公开、
   默认匿名"为什么）；修复要写**根因**，不能只写现象。
4. **已知取舍**（章节名可自定）：做不到的、留待下轮的、有风险的。
5. 涉及回滚的改动，给出回滚命令或 SQL。

不写内部重构细节（那属于工作报告）。

### 4.2 工作报告（`reports/`）

读者是**维护者与下一位接手的人**。必备：

1. **报告头表**：报告日期 / 项目 / 生产版本（Worker UUID **并列** git 短哈希）/ 对应更新记录。
2. **范围**：本轮做了什么、依据是什么（审计？需求？）。
3. **交付结论表**：`级别 | 问题 | 状态 | 关键证据`。证据必须是可复核的东西
   （测试文件名、命令输出、生产 URL）。
4. **工程状态**：逐条列出实际跑过的门禁与真实数字。
5. **确认无问题的部分**：审计过的、看起来可疑但查证没问题的，写下来，避免下一个人
   重复排查。
6. **已知限制与未做项**：分「需要人工操作的」「代码侧待办」「固有限制」三类。
7. **下一步建议**：按优先级排序，每条要能独立执行。

### 4.3 审计（`audits/`）

必备：审计范围与方法、逐条结论（`严重程度 | 位置 file:line | 问题 | 建议`）、
**已核实无问题的清单**、结论汇总。审计文档是**某一天的快照**，不在其中续写后续状态；
状态跟进写在更新记录或路线图里，并在审计文档顶部注明"结论可能已被后续迭代改变"。

### 4.4 手册（`guides/`）

面向操作，必备：适用场景、前置条件、可复制的命令、常见故障与排查顺序。手册要能
让一个没参与开发的人照着做完；写不出来的步骤说明还缺工具，补工具而不是写"自行处理"。

### 4.5 交接（`HANDOVER.md`）

必备：现状（一句话）、最近一次实质性变更、**最容易踩的坑**、接手第一步检查清单、
指向路线图的链接。历史内容超过一个季度就标注"以下为历史背景"并停止在其中追加。

### 4.6 路线图（`UPGRADE_ROADMAP_*.md`）

必备：当前基线（版本、迁移号、测试数）、阶段划分、每项带 `☐ / ✅ 提交哈希`、
验收标准、**贯穿约定**（门禁、红线）。已完成项保留不删——它是"为什么现在是这样"
的唯一记录。新路线图替代旧路线图时，旧的在顶部写"已被 X 取代"并移入 `archive/`。

## 五、链接与引用

1. **跨文件引用一律写仓库根相对路径**（`docs/guides/QUESTION_TYPES.md`），不写
   `../guides/xxx.md` 之外的相对跳跃写法；仓库内的站内链接必须可点击。
2. 代码注释里提到文档时，同样写完整路径。改了文档位置必须同步改代码注释。
3. 引用具体代码位置写 `src/foo.ts:123` 形式，方便定位。
4. **移动或重命名文档后，必须跑链接检查**（见下节），并在提交信息里写明范围。

## 六、提交前检查清单

```bash
node scripts/check-docs-links.mjs   # 文档链接全绿（469+ 处引用）
pnpm format:check                   # prettier，含 .md
```

- [ ] 标题明确了"这是什么"，不是"记录"、"说明"这类空标题
- [ ] 头部有状态/日期（长期文档用表格，一次性文档在标题下加日期行）
- [ ] 所有数字都有来源，没有估算值
- [ ] 未做项与已知限制已单列
- [ ] 没有密钥、Token、真实用户隐私数据（截图里也要检查）
- [ ] 新文档已登记进 [`README.md`](README.md) 的对应章节
- [ ] 链接检查与 `format:check` 通过

## 七、模板

复制即用。占位符用 `<>` 标注，写完后全文搜索一遍 `<` 确认没有残留。

### 7.1 更新记录

```markdown
# 更新说明 · <YYYY-MM-DD><（主题）>

> <2–5 行引语：用户能感知什么、修掉了什么隐患。>

| 项         | 值                                                 |
| ---------- | -------------------------------------------------- |
| 功能上线   | `<Version UUID>`（<HH:MM> CST）                    |
| 线上入口   | https://emoemok.top （国内）· https://emoe.eu.cc   |
| 数据库迁移 | <无新增 / 00XX_name.sql 已应用；老库缺列时……>      |
| 自动化测试 | **<N> 文件 / <M> 用例全绿**（上轮 <n>/<m>，+<d>）  |
| 静态检查   | 根 `tsc`、admin `tsc`、`eslint`、`prettier` 均通过 |

---

## 一、<面向用户的变化>

<结论先行。为什么这样设计 / 不这样做会出什么事。>

## 二、<修复>

<根因，不只是现象。>

## 三、已知取舍

<做不到的、留待下轮的。>
```

### 7.2 工作报告

```markdown
# 工作报告 · <YYYY-MM-DD>（<主题>）

| 项           | 值                                                |
| ------------ | ------------------------------------------------- |
| 报告日期     | <YYYY-MM-DD>                                      |
| 生产版本     | Worker `<UUID>`（<HH:MM> CST）· git `<短哈希>`    |
| 对应更新记录 | [`RELEASE_<日期>.md`](releases/RELEASE_<日期>.md) |

## 1. 本轮范围

## 2. 交付结论

| 级别 | 问题 | 状态 | 关键证据 |
| ---- | ---- | ---- | -------- |

## 3. 工程状态（实测）

| 门禁 | 结果 |
| ---- | ---- |

## 4. 确认无问题的部分

## 5. 已知限制与未做项

## 6. 下一步建议
```

### 7.3 审计

```markdown
# <范围>审计 · <YYYY-MM-DD>

> 快照性质：结论反映审计当日代码状态，可能已被后续迭代改变。

## 范围与方法

## 结论

| 严重程度 | 位置 | 问题 | 建议 |
| -------- | ---- | ---- | ---- |

## 已核实无问题

## 汇总与优先修复顺序
```

## 八、维护这份规范

- 规范不是摆设：新增文档类型时，先在本文档补一节再写第一份实例。
- 发现某条约定的操作成本过高（例如每次都要手改十几个引用），就补工具
  （如 `scripts/check-docs-links.mjs`），不要靠"记得改"。
- 修改规范时，在提交信息里写清"为什么改"和"受影响的既有文档是否已回补"。
