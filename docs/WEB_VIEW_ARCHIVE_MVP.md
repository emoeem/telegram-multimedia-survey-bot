# Telegram Web 视图层归档 MVP —— 设计与调研补充

> 对应 `TELEGRAM_ARCHIVE_RESEARCH.md` §7/§8/§14 方案 4 的 “Collector B（视图层采集）” 与附录 A 的
> “直接保存到自己的频道”。目标：**在官方 web.telegram.org 页面内运行用户脚本，把聊天归档到用户自己的私有频道，
> 全程不需要 my.telegram.org 的 api_id/api_hash**。
>
> 日期：2026-09-07。状态：方案已定，脚本为“探测优先”骨架，选择器需真机校准。

## 1. 为什么这条路不需要 api_id

web.telegram.org A/K 是 Telegram 官方托管的完整 MTProto 客户端。官方站点自己持有官方应用身份
（api_id/api_hash 不下发到页面配置），用户扫码/验证码登录后，浏览器里的页面就是这个“设备”。
用户脚本不新建连接、不伪造身份，只是操纵**用户已经登录的这个页面**，因此：

- 无 api_id/api_hash、无 my.telegram.org；
- 登录体验与官方网页一致（含扫码）；
- 受保护聊天的正文与媒体**已经下发到页面**（服务器视角：正常客户端会话），
  网页只是隐藏下载/复制入口 —— 脚本恢复的是“客户端行为”，与补丁官方 Desktop、LSPosed 同类。

## 2. 风险与边界（与主文档 §23 一致）

1. 非官方自动化仍是“非官方客户端语义”的行为，账号处于观察/风控范围；建议实验小号。
2. 恢复受保护聊天的“保存/转发”违背聊天所有者意图并违反平台规则；默认 skip，`allow_media` 逐聊天显式开启。
3. Telegram Web A/K 高频改版，DOM/内部结构会漂移；本 MVP 以“探测 + 可调选择器”缓解，不能保证长期稳定。
4. 页面必须保持打开；适合小批量/增量，不适合百万级无人值守全量。

## 3. 三条可行子路线（按实现难度/保真度排序）

| 子路线                  | 机制                                                     | 保真                    | 受保护                       | 风险/难度       |
| ----------------------- | -------------------------------------------------------- | ----------------------- | ---------------------------- | --------------- |
| F. 页面原生转发         | 调用页面自己的 forward 对话框（模拟选择频道 → 发送）     | 原文件、相册、转发头    | 服务器拒绝（无按钮/报错）    | 中；随 DOM 漂移 |
| C. 复制重发（文字先行） | 读取消息文本 → 切到频道 → 粘贴发送                       | 文字 100%；媒体需配合 M | 文字可（默认关）；媒体默认关 | 中              |
| M. 媒体下载重发         | 用页面内部 stream URL 分片取媒体 → File → 拖入输入框发送 | 原文件                  | 可（视 DC/保护实现）         | 高；最脆弱      |

MVP 建议：**F 为主（快、稳、官方语义），C 兜底文字，M 作为 `allow_media` 高级开关分阶段做**。

### M 路线的媒体取回机制（已调研验证）

Telegram Web 把媒体以同源内部地址下发，形如：

```text
stream/{"dcId":5,"location":{...},"size":...,"mimeType":"video/mp4","fileName":"xxx.mp4"}
```

参考项目 [Neet-Nestor/Telegram-Media-Downloader](https://github.com/Neet-Nestor/Telegram-Media-Downloader)
（用户脚本，GPL/MIT，仓库自述）的做法：直接用 `fetch(url, {headers:{Range:"bytes=N-"}})`
按 `Content-Range` 分片取回 Blob 并拼接——该地址经同源会话鉴权，服务器视角就是“当前登录的官方网页客户端在请求媒体”，
因此受保护聊天也能取到（网页只是隐藏下载按钮，媒体流地址仍存在）。

本脚本在其思路基础上做“取 Blob → 构造 File → 注入频道输入框（drop）→ 发送”，
而不是下载到本地。注意：若媒体元素已是 `blob:` URL（本地解码缓存），直接 fetch 该 blob URL 即可。

## 4. 架构

```text
web.telegram.org (A/K) 页面
  └─ Tampermonkey/Violentmonkey 用户脚本
      ├─ appDetector      : 识别 Web A / Web K
      ├─ probe            : 一键导出当前页 DOM 结构/选择器快照（校准用）
      ├─ collector(DOM)   : 按选择器读取消息（文本/媒体元素）
      ├─ forwarder(DOM)   : 原生转发对话框自动化（F）
      ├─ copyWriter(DOM)  : 文本复制到目标频道（C）
      └─ mediaFetcher     : stream URL → Blob → File（M，占位）
```

选择器策略：不是写死单一 CSS，而是 `config.selectors[app][chatType]` 可调；probe 输出会给出
候选元素样例（含 class 快照），第一次真机运行后据此校准。

## 5. 产品形态（MVP）

- 页面内悬浮控制条：目标频道、模式（forward/copy）、保护策略、开始/停止、进度。
- 单次运行范围：**当前聊天当前可见消息** 起步（几十~几百条），随后加“滚动翻页持续采集”。
- 幂等：本地 IndexedDB 记录 `(sourceChat, msgId)` 已归档，避免重复。
- 频道内格式（copy 模式）与 Telethon 版一致：`#chat_… #user_… #date_…` + 原文 + 来源行。

### 5.1 snapshot（气泡截图）模式 —— 用户建议的“聊天记录截图”路线

直接把每条消息气泡渲染成 PNG 发进频道：发送者名、时间、回复上下文、可见媒体一图包含，
对“禁止下载”频道同样可用（截的是用户已见内容）。实现用 html2canvas（用户脚本拿不到浏览器
原生元素截图 API，`captureVisibleTab` 仅浏览器扩展可用），与网页渲染效果一致。

### 5.2 增量截图工作流（按用户需求设计）

“每天只截新增，不从头再来”：

1. 每个聊天本地保存断点 `check:<peer> = {mid, ts}`，即上次成功发送到频道的最新消息；
2. **方向与 Telegram 一致**：新消息在底部，重进聊天会停在“上次阅读位置”（未读起点）。
   因此日常增量用「▼ 增量到最新」：从当前位置向下滚动到最新即可，不重复已读内容；
   「▲ 向上回溯」用于首次全量/补旧（从底部向上，遇断点或指定日期停止）；
3. 截图入库发生在源聊天页面（元素仍在 DOM 中），随后用户切到归档频道统一发送；
4. 媒体类消息（视频/图片/语音/文件）在发送前先输入 caption：`#media_视频 #date_2026_09_07`，
   图片附加后文字即成为该帖说明，用于在频道里按类型/日期检索；
5. 发送成功才推进断点；失败项保留在队列，可重试，不会漏。

滚动实现：自动定位包含 `.bubble` 的可滚动容器（无需硬编码聊天列表 class）；
向下模式以“到达底部（最新）”为终止，向上模式以“看到断点气泡或到达顶部”为终止。

### 5.3 流式“截图一张 → 发送一张”（0.3.0 起）

早期版本把截图全部塞进 JS 内存队列再批量发送，几百张 PNG 会吃满内存，且“批量”
与“每天只截新增”的目标矛盾。0.3.0 改为流式：

```text
源聊天 截图1 → 切到归档频道 发送1 → 切回源聊天 截图2 → ……
```

- 任意时刻内存里只有当前这 1 张截图；
- 队列只保存“失败/待重试”的元数据（失败项附 1 张截图用于重试）；
- 成功即从队列移除，失败保留、可手动重试，清理由用户显式执行；
- 日期解析不再依赖单一属性：`data-timestamp` → `time.datetime` → 元素 title → 时间文本，
  全拿不到则标“未知日期”，绝不退回“当前时间”；
- 模式记忆使用新存储键，避免旧版本遗留的 copy/forward 覆盖默认 snapshot。

## 6. 验证步骤（需要用户配合的真机流程）

1. 浏览器安装 Tampermonkey，导入 `tg-archive/web/tg-web-archive.user.js`；
2. 打开 web.telegram.org/a（或 /k），扫码登录；
3. 点脚本面板「探测 DOM」→ 把输出复制回开发侧，校准选择器；
4. 小规模验证：选一个测试聊天 + 私有频道，forward 2~5 条 → 确认；
5. 再开 `allow_media` 验证媒体复制；最后小批量滚动采集。

开发侧可用本机 Playwright + Chromium 打开同一页面（用户扫码），直接读取真实 DOM 完成第 3 步。

## 7. 明确不做（本 MVP）

- 不解析/不依赖 Telegram 内部 JS 私有对象（除 stream URL 读取外）；
- 不做全量百万级；不做多聊天队列调度；
- 不提供绕过“2FA/登录安全”的任何能力。
